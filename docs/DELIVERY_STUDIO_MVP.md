## 1. 产品边界与第一版成果

Delivery Studio 将一份婚礼项目的交付意图与素材，组织成经过检查的交付文档。

第一版的成功标准：用户可以创建项目、选方案、导入整个项目文件夹，系统建立可检查的素材关系，用户处理少量例外并确认视觉，然后稳定生成 PDF、长图或两者。

建议纳入 MVP：

- 项目列表、创建／复制项目、保存和重新打开。
- 客户／新人资料、工作室品牌、字段显示设置。
- 可编辑的交付项目、制作说明和其他交付文案。
- 少量内置方案，以及保存自己的方案。
- 文件夹扫描、明确的识别报告、对比图自动配对和人工修正。
- 两个模板位置及共享能力契约；本阶段只定义结构和研究方向。后续可用 MVP 建议提供两套完成的模板，具体美术另行设计。
- 核心对比布局 Split、Stacked；普通单图按需使用 Full Width。
- 实时内容预览、按输出目标检查、PDF 与长图导出。
- 文件失联后的重新定位、导出版本记录和失败恢复。

暂不纳入：Canva 自动填充、任意拖拽页面编辑器、AI 自动修图、视频转码、原片云盘同步、CRM、档期、完整生产管理、计费、多用户协作、Web 发布平台重建。

Web 只保留适配边界，后续接入现有 Worker。

## 2. 用户流程与页面结构

主流程：

```text
创建项目并选方案
    ↓
补充必要资料、确认本次交付内容
    ↓
拖入项目文件夹 → 系统扫描、分类、配对并形成报告
    ↓
自动采用明确无冲突结果、人工修正少量例外
    ↓
选择模板与布局 → 查看对应输出预览
    ↓
自动检查 → 选择 PDF／PDF + 长图／长图 → 导出
```

这不是必须逐页完成的向导。项目可以先导入素材再补资料，始终能返回修改，草稿自动保存并显示保存状态。

建议只有三个主要工作入口：

| 入口 | 用途 |
| --- | --- |
| 项目列表 | 创建、继续编辑、复制、归档、查看最近导出 |
| 项目工作台 | 完成一次交付；这是主要使用场景 |
| 工作室设置 | 品牌资料、我的方案、识别规则；低频使用 |

项目工作台建议采用三栏：左侧为交付文档模块导航，中间为按需编辑区域，右侧为预览。窄屏时预览切换为独立视图，不强行压缩三栏。

工作台内部提供「内容」「素材与对比」「视觉」三个切换项；预览和导出入口始终可见。导出前检查用侧栏或弹层，不另建复杂页面。

UX 原则：

- 默认从方案填好文案和结构，用户主要改差异。
- 导入后先显示摘要，例如“找到 12 组完整对比、1 张未配对图片、2 项交付内容缺少链接”；数字必须来自实际扫描。
- 完整结果默认折叠；问题项集中显示，并可跳转到对应字段或图片。
- 明确规则得到的完整配对不要求逐组点击确认；提供一处整批浏览与最终预览，只有冲突或弱线索才需要处理。
- 每个问题给出可执行操作，如交换、选图、重新定位、补链接、隐藏本模块。
- 自动结果提供简短原因，如“按当前规则：尾号 1 为 After”；用户无需理解匹配算法。
- 切模板不重置内容；重新导入不覆盖人工修正；重新应用方案前展示变更。
- 预览默认模拟手机阅读宽度；制作界面仍面向 Windows 桌面浏览器，不把客户阅读端和摄影师编辑端混为一套移动 UI。
- 本次不含调色对比时，不必创建空对比章节；已启用的对比章节却没有可展示内容时，应补图或由用户明确关闭，不能自动隐藏问题。

## 3. 五个需要先划清的边界

### 3.1 找到了素材，不等于承诺交付

文件夹中出现“音频”可以形成一条素材发现结果，但不能直接变成“向客户交付音频文件”。音频可能只是用于成片的制作素材。

Preset 和用户编辑决定本次交付承诺；扫描提供事实与建议。缺失检查将两者对照，而不是单方面推导。

### 3.2 没有本地文件，不一定缺少交付内容

“完整成片”可以通过百度网盘链接交付，无须读取或上传完整视频。反过来，找到本地文件但没有交付方式，也不一定已经可以交付。

交付项目应分别描述内容和交付方式：例如外部链接、附件、线下交接或仅作说明。链接只在对应交付方式需要时必填。

### 3.3 数据可以共用，输出需要各自排版

业务关系保留为：Project Data + Template + Layout = Output。

技术上补充显式的输出目标：

```text
项目数据 + 文档结构 + 模板版本 + 布局配置
                       ↓
              一次不可变的内容快照
                       ↓
        PDF RenderPlan / Image RenderPlan / 未来 Web RenderPlan
                       ↓
                 相应输出产物
```

PDF 有分页，长图有像素和长度限制，Web 有响应式和交互。输出目标独立于模板，但会影响可用布局及布局的具体表现。

### 3.4 项目草稿可以变，已经输出的交付版本应固定

客户资料、Logo、方案和模板之后可能修改。一次导出必须绑定内容快照、模板版本、已解析日期及资产版本，避免历史交付随当前编辑漂移。

重新生成旧版本需要原版本使用的资产仍然可访问；只有元数据快照不足以保证复现。因此保留文档实际用到的轻量图片和品牌素材，并标记复现所需资产是否完整。

### 3.5 可扩展不等于任意可编程

MVP 允许编辑、排序、显隐和组合已有模块，不提供任意 HTML、脚本、模板代码或完整自由排版器。先完成有限且稳定的文档类型。

## 4. 核心数据模型

这是概念模型，不是已经确定的数据库表清单。所有持久对象采用稳定 UUID；文件名、序号、客户姓名均不能作为主键。

| 对象 | 主要信息 | 边界 |
| --- | --- | --- |
| Workspace / Tenant | id、名称、默认时区 | 数据所有权边界；本机版只有一个默认工作区 |
| BrandProfile | id、tenantId、品牌名、Logo 资产、颜色、署名信息 | 与租户身份分离，便于未来 White Label |
| Client | id、tenantId、称呼、联系人／新人信息 | 客户的当前记录 |
| Project | id、tenantId、projectNo、clientId、婚礼日期、备注 | 一次婚礼项目的长期身份 |
| DeliveryDocument | id、projectId、客户展示快照、交付日期规则、模块、视觉及输出偏好 | 本次交付文档；MVP 每项目默认一份 |
| DeliveryItem | id、documentId、title、description、format、visible、order、交付方式与资源引用 | 可扩展的交付条目，不是一组 Boolean |
| ContentModuleDefinition | id、version、内容类型、默认标题／文案、系统或租户归属 | 可复用内容来源，应用时复制为实例 |
| ContentModuleInstance | id、documentId、type、标题、结构化内容、来源版本 | 制作说明、观看建议、修改说明等内容实例；章节显隐与排序归 DocumentBlock |
| Asset | id、tenantId、来源、用途、媒体元数据、可用性 | 资产身份，与具体位置分离 |
| AssetVersion | id、assetId、内容指纹、不可变媒体元数据、管理副本引用 | 区分同一资产被替换前后的具体内容 |
| Comparison | id、documentId、before／after 资产及版本引用、visible、order、标题／说明 | 一组业务对比关系；槽位指向明确的版本 |
| DocumentBlock | id、documentId、type、内容引用、visible、order、布局覆盖 | 文档中显示什么、顺序如何 |
| Preset | id、version、默认内容和默认展示配置 | 创建时复制初始值；可带可选视觉建议 |
| TemplateDefinition | id、version、设计变量、组件外观、默认布局和能力声明 | 视觉规则，不包含具体客户内容 |
| ExportRevision / ExportJob | 快照、模板版本、输出目标、任务状态、产物记录 | 已输出版本与执行过程分离 |

以上属于租户的数据都携带或通过严格约束确定 tenantId；不能因为对象已有 UUID 就省略归属检查。

表中的所属文档表示概念归属；实际父关系统一为 Document → Block → 内容实例／条目／Comparison，详见领域规格。Asset 的可用性概览由固定版本的 AssetLocation 推导，不另存与位置状态冲突的一份答案。

具体约定：

- Client 保存当前资料；DeliveryDocument 保存此次交付使用的客户／新人展示快照，避免旧项目被联系人改名影响。
- 项目编号可以按工作室规则生成，但只是业务编号，不是内部 ID。
- 婚礼日期使用不带时区的日历日期；创建、导出等事件使用时间戳。自动交付日期按工作室时区计算。
- 交付日期拆成取值规则（自动／手动）与 visible。自动值在准备正式预览候选时固定，提交校验通过后原样用于实际输出；隐藏自动日期不触发无意义的跨日预览重建。
- 备注区分内部备注与交付备注，默认内部备注不参与渲染。
- 核心内容采用明确字段和有限的模块类型，不把全部数据塞进一个没有约束的 JSON。
- 格式、大小、时长、封面、播放链接、下载链接等可作为 DeliveryItem 的结构化可选属性；播放与下载链接不能混成一个含义模糊的 URL。
- DeliveryItem 的 visible 和 order 属于条目；DocumentBlock 的 visible 和 order 属于章节，两者不是同一个层级。
- Comparison 也可作为集合条目独立显隐与排序。ContentModuleInstance 不再重复保存章节级 visible／order；引用它的 DocumentBlock 是唯一来源。
- 内容引用通过 ID 建立；布局配置放在展示配置中，不放进图片文件名或内容正文。
- 草稿允许缺字段、不完整对比。是否允许输出由当前可见内容和输出目标决定，不要求整个项目全部资料完整。

内置模板、布局及内容定义是带版本的只读系统资源；用户保存的方案和品牌配置属于租户。公共定义可被多个工作区引用，但不能混入客户数据，也不能被某个租户原地修改。

创建或复制文档时，Block、内容实例、条目、Comparison 都生成新 ID 并重映射引用。建议“复制为另一场婚礼”默认只带通用文案、结构和视觉，清空原客户、日期、交付链接与项目图片；明确选择保留的项目资料再按新项目归属复制。

MVP 不提前建设多文档管理 UI。DeliveryDocument 的独立身份只是避免未来把一个婚礼的不同交付批次全部挤进 Project。

## 5. Preset、Template、Component、Layout

| 概念 | 回答的问题 | 示例 |
| --- | --- | --- |
| Preset | 这次通常交付哪些内容？ | 完整成片、调色说明、保存建议的初始组合 |
| DocumentBlock | 本文档有哪些章节，按什么顺序？ | 客户信息、交付清单、调色对比、署名 |
| Component | 某类内容如何被稳定渲染？ | DeliveryList、ComparisonGallery、Signature |
| Template | 整份交付呈现怎样的视觉风格？ | 明亮编辑式、深色电影式两种暂定方向 |
| Layout | 这个模块内如何摆放内容？ | Split 左右、Stacked 上下、Full Width 单图 |
| RenderTarget | 输出到哪里，受什么介质约束？ | PDF、长图、未来 Web |

Template 由以下部分组成：

- Design tokens：字体角色、字号阶梯、颜色、间距、容器宽度、边距、边框、图片比例等。
- 组件样式：章节标题、正文、交付条目、对比标识、页脚、署名等。
- 默认布局：不同模块在不同输出目标下建议使用什么布局。
- 能力声明：支持的模块、布局、输出目标，以及内容过长时的处理规则。

Layout 只接受匹配的内容类型。Split 需要 Before／After，Full Width 需要一张图；不能用任意布局强行渲染任意数据。

建议第一版：

- 对比组件支持 Split 与 Stacked；客户主要用手机阅读，因此默认 Stacked。Split 可选，并检查并排后图片与标签是否仍可读；必要时单图组件使用 Full Width。
- 两个模板使用同一套内容类型与核心布局，降低切换成本。
- 模块顺序是文档数据，模板可以提供初始建议，但切换模板不得重新排序或删除用户内容。
- 对比图默认完整显示，保留 Before／After 标签。需要裁切时，两张图尽量使用同一裁切窗口，并明确预览。
- 图片比例不一致时提示；不能为了视觉整齐而默认把两张图裁成不再可比的画面。
- Overlay、Slider、Cinematic、Editorial 作为后续布局能力。Slider 适合 Web；PDF／长图若不支持，必须提示并映射为用户可确认的 Split／Stacked。

不要求所有未来模板都支持所有能力，但不兼容情况必须在选择阶段被发现，不能到导出时静默丢内容。

布局默认解析顺序为模块人工覆盖、文档默认、模板默认、组件默认；每层优先目标专用配置。显式选择不兼容时提出修正，不自动跳过该选择。MVP 先提供章节级布局覆盖，单组独立覆盖作为后续扩展边界。

LOG 工作流、肤色精修等可复用文案来自带版本的 ContentModuleDefinition，添加时复制成可编辑实例。第一版通过内置定义与自定义 Preset 复用，不必增加独立内容库管理页面。

## 6. Asset 模型与文件夹导入

### 6.1 资产身份、位置与派生结果分离

Asset 描述文件是什么，例如图像、视频、音频、Logo、对比源图。

AssetLocation 描述在哪里：

- 本地来源：importRootId + relativePath；设备本地的 RootBinding 管理目录授权或绑定。浏览器模式保存可用的目录句柄及授权状态，不假定能够取得绝对路径。
- 本机管理副本：文档实际用图存放在应用管理目录，以稳定存储键定位，重新打开项目不必依赖浏览器保留原目录权限。
- 管理存储：storageProviderId + bucket／objectKey 或等价定位信息；不保存会过期的签名 URL 作为永久地址。
- 外部引用：资源链接与提供方信息。百度网盘整包链接通常属于交付资源，不必伪装成某个单一媒体文件。

AssetDerivative 描述缩略图、预览图、面向导出的标准色彩图等，并记录来源版本和处理参数。

本地绝对路径不进入未来客户页面或跨设备共享的项目数据。文件移动后可重新绑定根目录；文件改名通过匹配或手动重新定位维持原 Asset ID。

同一资产的源文件被覆盖时，生成新的 AssetVersion 并提示可接受的更新。草稿中的 Comparison 也指向明确版本，不会因为源文件变化自动替换图片；用户接受后才更新对应槽位。历史导出继续引用历史版本，旧版所需资源失联时明确显示不可复现。

### 6.2 导入流水线

```text
选择／拖入文件夹并授予读取权限
  → 浏览器内的导入适配器遍历目录并收集轻量文件信息
  → 将分批索引提交给本机服务
  → 识别用途与可处理类型
  → 仅把文档需要的图片导入本机管理目录并建立预览资源
  → 运行 Comparison 规则
  → 对照本次交付配置检查缺项
  → 显示导入报告和可接受的建议
```

每一阶段有进度、数量和失败记录，可取消。读取失败不应阻止其他可读取文件被报告。

浏览器只负责在用户授权范围内取得文件与索引，分类、配对、冲突处理仍由应用层规则完成。网页拖入的文件不能自动转换为服务端可读的绝对路径。

第一版优先保证 Windows 上的现代 Edge／Chrome；拖入目录能力不完整时提供“选择文件夹”。保存的目录授权可能失效，重新扫描时应明确请求重新选择；已经导入的文档用图仍可继续编辑和导出。具体浏览器能力需要在实现前验证。

第一版建议保证常见 JPEG／PNG 对比图可处理；HEIC、TIFF、RAW 等在检查实际样本和运行平台后再决定支持范围。不支持的格式要列出，而不是消失在列表中。

性能与行为约束：

- 默认不拷贝、不上传、不转码完整婚礼视频，也不重命名用户源文件。
- 大型交付目录先统计文件和类型，不默认打开全部视频、计算全部原片完整哈希。
- 对实际使用的对比图片可以计算内容哈希用于去重与版本识别；其他文件先使用大小、修改时间等轻量信息，且不把它们当作内容一致的证明。
- 大目录采用受限并发、渐进结果和增量扫描；缩略图列表按需加载。
- 不因“存在某个目录”就宣布对应交付已经完整；系统只能验证它知道的要求。
- 未知文件归入待分类／忽略清单；符号链接和异常目录循环不默认跟随。
- 外部链接离线时标为“尚未验证”，不能把没有验证过的访问权限报告为有效。

## 7. Comparison：自动识别与人工接管

Comparison 至少包含：

- 稳定 id、所属交付文档、顺序、标题／说明。
- Before 与 After 槽位各自引用 assetId 和 assetVersionId；草稿中允许任一槽位为空。
- 匹配来源、规则版本、建议原因。
- 人工确认／覆盖记录，与自动推断结果分开保存。

配对完整性与审核状态分开：一组图可能完整但尚未确认，也可能经过人工处理但仍缺一张图。不要用一个状态字段表达所有情况。

建议的匹配优先级：

1. 已确认的人工关联或显式项目映射。
2. 用户选择并已确认的命名规则。
3. 内置 before／after 规则等明确、无歧义的规则。
4. 文件时间、相似名称等较弱线索，只形成建议。

当前的 `01-1 / 01-2` 规则做成可保存的识别规则，其中 `-1 → After`、`-2 → Before` 可修改。系统解析出临时分组键后生成 Comparison ID；以后改名、改顺序，Comparison ID 都不变。

分组必须考虑导入根和相对目录。同名文件、同一编号多个候选、不同目录重复编号、JPEG／PNG 双份、多个规则冲突，都不能采用“最后一个覆盖前一个”。

明确且唯一的结果可自动建立关系；弱线索、冲突与缺对必须进入待确认列表。无需第一版引入 AI 视觉配对或无法解释的置信度百分比。

人工修正应支持：

- 交换 Before／After。
- 向任一槽位拖入／选择图片。
- 拆开错误组合、合并未配对图片、新建空对比。
- 替换失联图片、调整顺序、排除本次文档不用的图片。
- 批量应用明确的命名规则，并在提交前查看影响。

重新扫描只增加发现结果、检测变化，不覆盖已经确认的人工关系。重复导入同一批文件不应不断创建重复资产和重复 Comparison。

被排除的文件或配对建议应保留项目范围的排除标记；重扫不能自动复活。修改识别规则可以产生新建议，但恢复已排除内容必须是明确动作。隐藏 Comparison 与删除源文件是不同操作。

## 8. 检查系统：让错误可见且可以处理

检查不是 UI 临时弹窗，而是独立的应用能力。编辑、预览和导出都调用同一组检查规则。

每个 Issue 包含 code、severity、关联对象／字段、原因和可用修正操作。消息面向用户，底层日志保留技术细节。

| 等级 | 例子 | 行为 |
| --- | --- | --- |
| 阻止输出 | 可见对比缺图、图片无法解码、所选目标不支持当前布局 | 修复、替换布局或明确隐藏相关模块后继续 |
| 需要确认 | 图片分辨率偏低、外链未验证、比例不一致 | 展示具体影响并确认；相同版本无需反复确认 |
| 提示 | 未使用素材、自动套用了已知规则 | 可查看，不增加不必要的步骤 |

仅按本次输出实际使用的内容判断阻塞。隐藏且未引用的坏图不会阻塞整个项目；隐藏关键模块应明确更新输出摘要，不能系统自行隐藏来绕过失败。

最终检查应包含：内容占位符、必需字段、图片可读性、配对完整性、字体是否就绪、版面溢出／裁切、链接的已知状态、输出体积与尺寸预算。

导出前再次检查本次固定资产版本的管理副本及其完整性。源文件移动或删除但管理副本完整时，继续使用已选版本；管理副本损坏或缺失才阻塞依赖该图片的输出。所有失败都保留草稿、指向原因，并支持重试。

检查结果区分全局问题与目标问题。客户必需字段缺失会影响两种输出；只有 PDF 的分页问题不能阻止用户明确选择仅生成长图。若选择双输出，共用输入有效且至少一个目标已通过预检，可明确选择“先生成可用目标”，并保留另一目标阻塞的状态。双输出任务不能静默降级为单输出成功。

## 9. PDF 与长图输出系统

### 9.1 共享内容，按介质生成计划

建议使用受控 Chromium 的 HTML／CSS 渲染链路。项目核心逻辑不依赖 Chromium，通过渲染适配器调用。

```text
先等待当前编辑成功保存并取得版本回执
  → 读取该已保存草稿并检查其修订号
  → 准备正式预览候选：解析并固定内容、资产版本、日期、模板版本
  → 解析为允许输出的展示数据
  → 按 PDF／长图生成 RenderPlan
  → 等待字体与图像就绪并检查排版
  → 正式预览与提交前复核候选依赖
  → 提交为不可变 ExportRevision 并启动各目标任务
  → 渲染到暂存位置
  → 验证文件并记录 Artifact
  → 完成对应输出任务
```

一次选择 PDF + 长图，两种产物必须来自同一个快照。如果一个失败，明确显示“部分完成”，可单独重试失败目标；不能笼统提示全部成功。

“导出最新草稿”的应用用例必须先提交并等待当前编辑命令保存成功。仍有未保存修改、保存失败或冲突时，不能因为数据库旧修订号尚未变化就提交旧候选；界面禁用按钮只是这一规则的展示，不能代替应用层校验。历史版本重导是明确选择旧版本的独立操作。

未提交的正式预览候选会因编辑、接受新资产版本或可见自动日期跨工作室日历日而失效。系统重建候选并标出变化，不能导出用户已经看过但已过时的版面。已提交的交付版本及其后续重试保持原日期和内容；导出期间的新编辑留在草稿，不混入正在生成的文件。

### 9.2 PDF

- 使用 Chromium 打印生成 PDF，保留文字的可选择性与链接能力，不把每页先做成整张截图。
- 第一版只支持一种手机优先的竖版页面规格；建议以 9:16 作为试排起点，再用真实内容验证，暂不定为最终尺寸。视觉模板不决定纸张／页面尺寸。
- 在约 360–430 CSS 像素的手机显示宽度下检查正文、Before／After 标签和链接的可读性；不以桌面放大预览判断交付质量。
- 用有限的模块分页规则管理标题跟随正文、Comparison 成对保留、页边距和必要的页脚。
- 不能只依赖 `break-inside: avoid`：超出一页的模块需要明确的缩放、拆分或报错规则。
- 竖图上下排列可能无法在同页保持清晰可读。此时可建议受控的连续两页展示，保留同组编号及 Before／After 标识；用户按文档确认分页策略并在正式预览中查看，不能静默缩小到不可读，也不需要每组重复确认。
- 排版预览显示最终页面边界。正式预检使用与导出相同的 Chromium 版本、字体和渲染组件。

### 9.3 长图

- 使用独立的连续画布计划，控制导出宽度、缩放倍率、质量与颜色空间；可先用 1080 像素宽做试样，再按实际发送渠道的压缩和阅读效果调整。
- 建议默认使用适合照片的高质量 JPEG；是否提供 PNG 取决于实际分享需求。
- 长图不是把 PDF 页面简单拼接；不保留无意义的分页空白和重复页脚。
- 分块渲染并按安全尺寸合成，避免一次截图造成内存峰值。
- 同时检查最终图像的像素总量、长度和编码限制。分块截图不能消除最终编码与客户端查看限制。
- 超过限制时给出清晰选择：分成多张长图或降低输出尺寸；用户尚未确认时不静默改成多张，也不裁掉尾部。
- 长图没有可点击链接。建议对需要客户访问的交付链接默认生成带用途标签的二维码与取件说明；仅编码授权显示的稳定分享地址，不编码内部凭据或临时 S3 签名地址。实际发送后不可识别时需明确替代访问方式，不能把图片里的网址画成可点击按钮。

### 9.4 预览与色彩

- 编辑时使用轻量实时预览；进入输出检查后，生成所选目标的正式预览。内容一致不等于 PDF、长图和未来 Web 的每个像素都相同。
- 浏览器字体、系统字体和渲染版本可能造成偏差，优先随应用提供许可明确的中西文字体。
- 规范处理 EXIF 方向和 ICC 色彩配置，派生为明确的 sRGB 文档资源，保留原始图片。
- 不对 Before／After 额外做自动美化、自动色调或锐化来“统一风格”。
- 已确认主要供手机阅读，因此 MVP 按屏幕交付验证；若后续需要印刷，需另定色彩与尺寸规范。

### 9.5 版本与可恢复性

- 项目修改后，之前的导出仍保持原样；新导出生成新 revision。
- 保存内容快照、所用轻量资产、模板与渲染器版本、输出配置和产物校验信息。
- 对历史版本只保证在依赖可用且版本受支持时可重新生成；不承诺跨操作系统和任意 Chromium 更新后文件逐字节相同。
- 任务执行失败不能破坏已有成功产物。中断任务可标记并重试，不必在 MVP 建设完整任务队列集群。
- 导出成功仅表示文件已生成；“已发给客户”是另一项业务事件。

## 10. 项目存储、工程结构与技术栈

### 10.1 根据已确认条件建议的运行形态

Windows 本机保存项目资料，客户主要手机阅读，未来确定使用浏览器登录管理。因此建议第一版就提供浏览器工作台，由同一电脑上的本机服务承担持久化、图像处理和正式渲染。

```text
现在：Windows 浏览器工作台
           ↕ 本机接口
      本机服务 → SQLite／文档用图／Chromium 导出

未来：浏览器工作台 + 云端登录
           ↕ 受认证与租户隔离保护的接口
      云端服务 → 项目元数据／必要文档资源／渲染任务
           ↕ 按实际需要配置
      百度网盘完整交付链接／用户 S3 短片
```

应用采用模块化单体：一个服务、清楚的内部模块和少量适配器，不提前拆微服务。

第一版建议打包为 Windows 一键启动入口，启动本机服务并打开浏览器；对用户交付时不要求先安装 Node 或手工执行命令。生产版由本机服务提供构建后的页面与接口，开发服务器不是发布运行方式。

本机暂不需要账号系统，但服务只能供本机授权页面访问。未来把接口迁入云端时再加入账号、租户校验和存储迁移；不能简单把本机服务公开上网。

本机工作台应使用稳定的 loopback origin，并处理端口占用，不随机更换端口后仍假定浏览器保存的目录句柄可用。目录句柄及授权只属于当前浏览器环境；本机服务与数据库是项目资料的持久来源。多个标签页编辑同一项目时使用修订号检查，禁止后保存的一页无提示覆盖前一页。

文件夹导入从第一天按浏览器权限模型设计。目录遍历和文件读取在 Windows 浏览器授权范围内发生，本机服务收到索引和必要的文档用图。未来服务位于云端时沿用该流程，但上传文档素材前须清楚显示文件范围和体积；完整视频默认仍不上传。

如果未来要求关闭网页后持续监控本机目录，才需要额外的本地连接程序；这不属于当前 MVP。

### 10.2 建议技术栈

- UI：React + TypeScript，Vite；交付工作台面向 Windows Edge／Chrome。
- 数据契约：TypeScript + Zod 或同类运行时校验；用于导入、持久化读取、渲染输入与未来 API 边界。
- 本机服务：Node.js LTS + Fastify 或同等轻量 HTTP 框架，提供页面、项目接口和导出任务接口。
- 应用层：独立 TypeScript 用例，负责方案应用、识别、配对、检查、生成快照和启动导出；浏览器文件访问封装为输入适配器。
- 初期本地持久化：SQLite 加明确迁移，媒体派生文件存文件系统，不放进数据库。
- 图像处理：Sharp 或同类成熟库，负责缩略图、方向、颜色转换和安全尺寸处理。
- 输出：Playwright + 固定版本 Chromium，由本机服务执行；Windows 安装／启动方案包含必要运行时，明确更新与体积成本。
- 云端演进：按实际需求采用 PostgreSQL、私有对象存储和受控渲染任务；不在第一版安装这些设施。

当前建议不另外引入 Electron／Tauri 宿主，先保持浏览器工作台的使用方式。Windows 安装器、启动入口和依赖打包仍需要在首次交付前验证，不把它们误认为浏览器应用自动解决的问题。

SQLite 到 PostgreSQL 需要真实的迁移工作；正确的存储边界可以控制修改范围，不能宣称换一个数据库地址即可成为 SaaS。

### 10.3 建议工程目录

以下是后续实现时的边界示意，当前不创建空工程：

```text
ZHFLIM/
├── docs/                       # 产品背景、设计、后续决策记录
├── src/
│   ├── domain/                 # 核心模型、业务约束
│   ├── application/            # 导入、配对、方案应用、检查、导出用例
│   ├── ui/                     # 工作台、编辑器、预览与问题提示
│   ├── rendering/
│   │   ├── components/         # 受控的文档组件
│   │   ├── layouts/            # 按内容类型划分的布局
│   │   ├── templates/          # 带版本的视觉配置
│   │   └── targets/            # PDF／长图，未来增加 Web
│   └── infrastructure/         # SQLite、文件系统、图片处理、Chromium
└── tests/fixtures/             # 经允许且脱敏的典型／异常素材样本
```

依赖方向是 UI 调用应用用例，应用依赖领域模型与接口，基础设施实现接口；渲染读取专用展示数据。UI 不直接把文件名匹配规则写进组件，也不直接修改数据库。

只有真实出现独立部署或复用需求时，再将模块提取成 package。

### 10.4 用户数据目录

```text
工作区数据/
├── workspace.sqlite            # 当前可编辑数据的唯一事实来源
├── documents/assets/           # 实际进入文档的图片与品牌资源，按版本保留
├── cache/                      # 可重新生成的缩略图与预览
├── exports/<projectId>/<revisionId>/
│   ├── snapshot.json           # 不可变导出快照
│   ├── manifest.json           # 使用版本、产物状态和校验信息
│   └── ...                     # PDF／图片文件
└── backups/                    # 可恢复备份；格式与保留策略待定
```

源素材目录原样保留。应用只管理必要的文档素材副本、派生资源与输出；不创建完整婚礼原片的第二份库。

数据库与媒体引用需要一致的备份／恢复方式；不能把复制正在写入的 SQLite 文件当作完整备份，也不能只备份元数据就宣称全部图片可恢复。

若后续增加可移交的项目包，JSON 是导出／交换格式，不与 SQLite 同时成为两套可编辑主数据。

## 11. SaaS、White Label 与未来 Web Delivery

第一天应保留：

- tenantId、稳定对象 ID、明确的归属关系和客户端展示快照。
- WorkspaceContext：本地只有一个固定工作区；未来由认证后的成员身份提供。
- 带租户范围的读取与写入接口，禁止跨租户的 Project／Asset／Comparison 关联。
- BrandProfile 与内容分离，Logo、颜色、署名可以替换。
- 存储位置、渲染、文件导入与业务逻辑之间的适配边界。
- 持久数据 schemaVersion、模板版本与迁移规则。

第一天不建设：复杂 RBAC、域名绑定管理、订阅计费、租户运营后台、多区部署、跨服务事件总线。

本机版的 tenantId 是结构准备，不是已经完成 SaaS 安全隔离。云端上线前必须补齐认证、授权、租户范围查询、对象存储权限、任务／缓存隔离与自动化隔离验证；PostgreSQL RLS 可作为额外防线。

对未来 Worker 的建议：

1. 先保存原始模板和配置说明，排查并移除其中可能存在的凭据；不先重写视觉。
2. 从同一交付快照生成 Web 专用展示数据，并映射到原模板的新人、日期、影片和品牌位置。
3. Web 发布增加独立的 Publication：绑定交付版本、唯一链接、访问策略、状态、过期／撤销设置。
4. 密码校验在 Worker／服务端完成，存安全散列并限制尝试频率；不能只用前端遮罩隐藏内容。
5. 短片和预告继续使用用户 S3。若要求内容受密码保护，S3 对象也需要私有访问控制或有效期受限的访问方式；公开固定视频地址会绕过页面密码。
6. 百度网盘保留完整交付资源的外部链接及按需显示的取件说明；SaaS 不代理上传整套原片。

隐藏字段、内部备注、绝对路径和存储凭据在构造展示数据时就排除，不能只靠 CSS 隐藏。内容组件采用受控结构并安全转义；导出渲染器不任意抓取外部 URL。

本机服务若被采用，应只绑定本机并限制来源／请求权限；未来远程服务必须重新设计认证和资源访问，不能直接把本地端口开放到公网。

## 12. 向 Wedding Production OS 演进

建议按真实需求逐步扩展：

1. Delivery Studio：本机浏览器工作台、交付草稿、素材引用、Comparison、模板、导出版本。
2. 云端浏览器管理：账号、数据迁移、必要文档素材存储、可靠的租户边界；满足用户已明确的长期使用方式。
3. Web Delivery：接入现有 Worker、发布版本、客户访问和撤销。
4. Projects／Production，再按需增加 CRM／Calendar：沿用 Project 和 Client 身份，扩展生产、订单与档期。
5. 对外 SaaS：多工作室成员权限、White Label 管理、订阅计费。

这些是可调整的演进方向，不是必须按顺序完成的技术依赖；云端管理与 Web Delivery 可以根据最先出现的实际需求交换顺序。云端个人后台不等于已经完成对外 SaaS，后者需要独立的安全和运营验收。

云端迁移时需要明确迁移 Project／Client 等元数据和文档用图、保持原 ID、验证资产完整性，并将本地目录授权标记为设备专属。完整视频保持现有存储，不能自动跟随数据库迁移被上传。

边界正确的标志：新增档期不需要重写 Comparison；新增模板不改交付条目业务规则；增加 S3 不改项目身份；新增 Web 不复制一套客户资料模型。

## 13. 建议实施节奏与验收

实施前先做两件设计工作：核对本文件中的暂定选择；用一份真实交付模板和一组实际素材验证字段、内容长度、阅读比例与识别规则。

后续实现建议分为四个可验收增量：

| 增量 | 可操作成果 | 主要验收 |
| --- | --- | --- |
| 1. 最小交付闭环 | 建项目、编辑内容、手工配对、一个模板、PDF | 保存后能重开；内容、图片和导出对应正确 |
| 2. 自动整理与修正 | 文件夹扫描、规则配对、导入报告、修正界面 | 缺图／重名可发现；人工关系不会被重扫覆盖 |
| 3. 完整 MVP 输出 | 第二个模板、核心布局、三种输出模式 | 切模板不丢内容；双输出同版本；长图过长有可用处理 |
| 4. 交付可靠性 | 资源重新定位、版本记录、字体／色彩预检、失败恢复 | 大目录响应可接受；中断可恢复；历史产物不被覆盖 |

三种输出模式是用户明确要求；后续可用 MVP 建议完成两套模板，第一个实现增量只是内部验证。本次任务只交付产品架构、规则及验收设计，不生成实际视觉模板或可运行应用，也不以它们作为本次设计完成的证明。

测试集中于有实际风险的行为：误配／缺对、重复导入、人工覆盖、文件变更、内容溢出、字体缺失、PDF 与长图版本一致，以及未来云端的租户隔离。不为低风险配置编写重复实现细节的测试。

需要通过真实样本制定性能和质量基准，当前不虚构“几万文件几秒处理完”或“完全像素一致”的承诺。

## 14. 当前待定决策

1. 已知方向是 Windows 本机资料、浏览器工作台、未来云端登录；具体启动／安装体验需要通过 Windows 原型验证。
