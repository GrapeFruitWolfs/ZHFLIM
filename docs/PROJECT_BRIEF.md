# Wedding Production OS：项目背景与设计基线

状态：根据用户原始说明整理的需求基线。未经过用户确认的具体实现方案放在 `DELIVERY_STUDIO_MVP.md`，不视为既定决定。

## 1. 产品目标

从个人婚礼摄影／摄像交付工作出发，逐步建立 Wedding Production OS，未来可能成为面向婚礼摄影师和工作室的 SaaS。

第一阶段是 Wedding Delivery Studio：把一次交付的内容、素材和视觉组织成可靠的交付文档。Canva 是现有设计工具和内容参考，不是系统的核心依赖，也不是产品边界。

用户应该主要决定：

1. 这次交付什么？
2. 采用什么视觉？
3. 结果是否正确？

整理、识别、匹配、排版、生成、检查和未来的发布，应尽可能由系统完成。目标是减少没有必要的思考和判断负担，不只是减少点击。

## 2. 已确认的第一阶段要求

- 支持客户称呼、新人信息、婚礼日期、交付日期、摄影师／工作室、项目编号、备注等项目资料。
- 交付内容、制作说明、观看／保存建议、修改说明、署名等采用可配置、可复用的内容模块。
- 已提及的现有内容包括：婚礼完整成片、航拍素材、音频处理、LOG 工作流、肤色精修、叙事音频优化。具体文案和实际模板尚未提供，不能假定已经掌握。
- 支持方案／Preset，方案只提供初始配置，应用后仍可自由修改。
- 支持整项目文件夹导入，自动报告找到了什么、缺少什么，以及哪些需要人工确认。
- 调色对比的内部对象是 Comparison，包含 Before 与 After 素材引用。
- 当前 `01-1 = After`、`01-2 = Before` 是一种可配置的导入约定，不是系统固有规则。
- 未来应兼容 before/after 命名、其他文件名、手动拖图和手工配对。
- 自动识别、人工修正、缺失提示是同一个完整流程；不允许静默失败。
- Template 决定整体视觉，Layout 决定模块排版，输出方式独立选择。
- 第一版预留两套通用视觉模板，具体美术方案后续专项设计。
- 第一版只实现少量核心图片布局；其余布局按输出能力逐步加入。
- 输出支持：只生成 PDF、PDF + 长图、只生成长图。
- 字段支持显示／隐藏；交付日期支持自动值、手动值和不显示。
- 核心对象采用稳定 ID；个人习惯不能成为不可修改的业务规则。
- UI 不承担核心业务逻辑；小步开发，优先稳定、清晰和可扩展。

## 3. 素材与存储边界

常见来源目录示例：

```text
项目/
├── 01_交付/
│   ├── 完整成片/
│   ├── 航拍/
│   └── 音频/
├── 02_调色对比/
│   ├── 01-1.jpg
│   └── 01-2.jpg
└── 03_其他/
```

目录和文件名用于识别输入，不能直接成为业务数据结构。该目录结构是当前示例，不能成为导入的唯一合法结构。

- 婚礼完整素材主要存放在百度网盘。
- 只有预告和短片进入现有 Worker Web Delivery，文件存放在用户自己的 S3。
- Wedding OS 管理项目、客户、内容、元数据、状态、链接和权限。
- 不默认把几十 GB 的原始婚礼素材上传到 SaaS；扫描文件夹不等于上传文件夹。
- 需要区分源素材、文档用图、派生缩略图、外部交付链接和导出产物。

## 4. 视觉方向与未来 Web

从 Apple、Editorial、Luxury、Leica、高端摄影工作室等方向研究信息层级、留白、字体、图片比例、间距和节奏，建立自己的 Design System，不照搬品牌。

用户已有 Cloudflare Worker Web Delivery 模板，后续应保存并适配，不在当前阶段重做。已描述的视觉包括深色、电影感、Editorial、Luxury、Minimal，以及品牌、A STORY IN MOTION、Wedding Story、新人姓名、日期、Private Viewing、影片内容等。

最终 Web Delivery：摄影师／工作室登录后台；客户通过唯一链接和密码访问，无须注册。

## 5. 长期演进方向

客户订单 → 档期 → 纳入后台 → 客户项目 → 拍摄 → 素材整理 → 后期 → 交付 → PDF／长图／Web → 客户访问 → 归档。

未来可能有 CRM、Projects、Calendar、Production、Assets、Delivery、Templates、Web Delivery、Analytics、Users、Billing。当前不建设这些模块的完整功能。

为 Multi-tenant 和 White Label 保留正确边界：每个工作室可以拥有自己的品牌、Logo、颜色、域名、模板、项目、客户和交付页；各租户的数据和资源必须隔离。第一版不因此引入复杂计费、团队权限和域名管理界面。

## 6. 不可破坏的设计原则

1. 项目数据与视觉展示分离。
2. Template、Component、Layout、输出目标有清楚的职责。
3. 文件名只是识别线索，核心对象通过 ID 关联。
4. 自动化结果可解释、可检查、可修正；人工决定优先保留。
5. 缺失、冲突、识别失败、导出失败必须明确呈现。
6. Preset 是初始配置；修改方案不能暗中改动已有项目。
7. Metadata 与实际资产分离，不依赖某一个网盘或对象存储商。
8. 新增视觉模板不应修改交付业务规则。
9. 不把导出成功等同于客户已经收到交付。
10. 现在只完成产品与技术设计，不编写业务代码、搭建工程或重做现有 Worker。

## 7. 仍需共同确定的事项

- 第一版的具体安装／启动体验，以及何时接入云端账号与管理。
- 实际模板中的完整文案、代表性图片、Logo、字体与使用授权。
- 第一批真实目录样本及常见异常：重名、缺对、竖图、混合格式等。
- 字段必填规则、默认交付方案、模板的具体视觉和长图分段偏好。

这些问题影响具体设计，但不改变上述产品目标和架构边界。

## 8. 用户补充确认

- 客户主要在手机上阅读交付内容。
- 用户的工作平台是 Windows。
- 当前项目资料保存在用户自己的电脑上。
- 后续确定需要通过浏览器登录和管理；是否做成对外 SaaS 仍是长期可能性。

据此，设计草案建议第一版就使用浏览器工作台，由 Windows 本机服务提供持久化与导出能力；未来再接入云端认证和管理。这是对已确认条件的技术建议，不代表用户已经选定具体框架或安装方式。
